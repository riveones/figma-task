### 2.2 Съёмка (Playwright)

- Dev-сервер: в design-lab — `preview_start` (`portal`), не Bash; в другом репо — как там принято, или адрес от человека (стенд).
- Viewport **1440×1066** (пропорции карточки 1000×740), `deviceScaleFactor: 2`, `reducedMotion: 'reduce'`. Даты, зависящие от «сегодня», — `page.clock.setFixedTime(...)`.
- Скрипт в `.claude/personal/<KEY>-figma/` (gitignored, переживает перезагрузку; в репо, где эта папка не игнорируется, — дописать `.claude/personal/` в файл `git rev-parse --git-path info/exclude`: локально, не коммитится), `require` Playwright по абсолютному пути из `node_modules` репо. Рабочий пример — `scripts/examples/` мода (`dp2871-capture.cjs`, `dp2871-devboxes.cjs`), обвязка — `scripts/lib.cjs`.
- Ревью — контактными листами (HTML-сетка миниатюр → один скриншот), а не по одной картинке.
- Для «For dev» тот же прогон отдаёт ещё и `boundingBox()` каждого размечаемого элемента (CSS px) → JSON; рамки проверять наложением на скриншот до переноса в Figma.

### 2.4 Загрузка скриншотов

С модом — инструмент `upload_screens { fileKey, pageId, items: [{ path, nodeId }] }`: всё ниже он делает сам. Если он ответил, что ссылки на загрузку получить не удалось (в auto-режиме вызов Figma MCP изнутри инструмента может остаться без решения классификатора), — вызвать `upload_assets` самому (те же `fileKey`, `count`, `nodeIds`, `currentPageId`, `scaleMode: FILL`) и повторить `upload_screens` с теми же `items` и `uploads` из его ответа (до 60 за вызов): файлы отправит мод. Без мода:

`upload_assets(fileKey, count, nodeIds=[ID заглушек], scaleMode: FILL)` → одноразовые URL (10 минут, ≤ 60 за вызов, ≤ 10 MB на файл) → POST каждого PNG как `multipart/form-data` с полем `file` (параллельно, `xargs -P 8`). Ответ 200 = картинка стала заливкой своего прямоугольника.

### 2.6 Перепроверка сопоставлений (обязательно)

Первый проход ошибается: на DP-2871 независимая перепроверка нашла 10 неверных строк из 47, а при пересборке под 20.0.0 (2026-10-09) — ещё 3 неверных и 12 неточных из 60 (Tabs как сегментный переключатель, `_DropMenu.CheckboxItem`, `CardCollapsible`, счётчик через `props.label.slots.right`…). Поэтому после 2.5 — **второй агент, без доступа к выводам первого «на веру»**, по методу:

1. **Версия:** пин в `origin/master:package.json` Portal (после `git fetch`) = версия скачанной копии кита. Не совпадают — сопоставлять нельзя: сначала скачать пиненную.
2. **Полный список экспортов:** `types/index.d.ts` → `components/`, `utils/`, `hooks/`; каждый `export * as X` (Table, Notification, _DropMenu, _Drop, Modal, Sidebar…) раскрыть до членов; сверить с export-блоком в конце `es/index.js`. Папки без экспорта — внутренние, использовать нельзя.
3. **Искать по функции, а не по имени:** grep по типам (`slots`, `onBack`, `width`/`onWidthChange`, `CheckboxItem`, `search`, `indeterminate`, `hasTime`, `orientation`, `maxLength`, `Group`). **Всегда раскрывать `Overrides.PropsSlice<'x',…>`** — они добавляют `classes.x` / `props.x` / `slots.x` и прячут возможности. Где решает поведение — открыть `es/components/*.js`.
4. **Прод-прецедент:** все импорты из `@sweed/fe-portal-kit` по `origin/master` (`git grep`, `sort | uniq -c`) + обёртки в `src/shared/components`. Экспорт, которого master ещё нигде не импортирует, помечать: готового примера в проде нет.
5. **Другие версии кита:** если рядом есть копии других версий — `diff -rq` типов с пиненной; что есть только в другой — писать отдельно («In <версия>: …»), не выдавать за доступное.
6. **Класс каждой строки:** Direct / Composition / Closest / Not in kit; ссылка на строку `.d.ts` и на один прод-файл.

Правки перепроверки вносятся в For dev до показа пользователю; в шапке For dev — строка «re-checked by an independent pass, <дата>».
